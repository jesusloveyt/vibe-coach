# 기여 가이드

**개발 경험을 초보자가 AI와 함께 따라갈 수 있는 학습 과정으로 만들어 주세요.** Vive Coach는 프로그램을 요청하고, 결과를 확인하고, 개선하는 경험을 제공하는 안내 콘텐츠 모음입니다. 기여자의 역할은 주제를 구현하는 것과 함께, 개발자의 설명 없이도 학습자가 진행할 수 있도록 코칭 과정을 다듬는 것입니다.

이 문서는 기여 절차의 초안입니다. 실제 제작 과정에서 발견한 불편과 개선 제안도 함께 보내 주세요.

## 먼저 작은 주제 하나로 시작하세요

`solutions/<주제명>/`에 학습 과정을 만듭니다. 처음에는 README.md와 AGENTS.md만으로 초안 PR을 제출해도 됩니다. 대화 예시는 실습을 거쳐 나중에 추가할 수 있습니다.

주제를 정할 때 다음을 짧게 적어 보세요.

- 누가 참여하며, 무엇을 할 수 있는 상태에서 시작하나요?
- 어떤 결과물을 만들고, 어디까지 완성하나요?
- 학습자가 직접 하는 일은 무엇인가요?
- AI가 언제 구현하고, 언제 질문하거나 기다려야 하나요?
- 무엇을 확인하면 학습 목표를 달성했다고 볼 수 있나요?

기존 사례로 [Calculator](../solutions/calculator/README.md)는 일부 내용과 계산 로직의 직접 수정을, [Resume](../solutions/resume/README.md)는 코드와 화면의 점진적인 확장을 다룹니다. 모든 과정이 같은 학습 방식일 필요는 없습니다.

## 파일의 역할을 나누세요

| 파일 | 역할 | 추가 시점 |
| --- | --- | --- |
| `README.md` | 학습자가 읽는 시작 안내 | 초안부터 작성 |
| `AGENTS.md` | 코딩 AI 에이전트가 읽고 따르는 현재 권장 코칭 지침 | 초안부터 작성 |
| `dialogues.md` | 학습자가 참고할 대표 대화 | 실습 기록이 준비되면 추가 |
| `maintainer-notes.md` | 다음 기여자를 위한 아이디어, 결정 이유, 메모, 이슈와 검증 기록 | 공유할 제작 경험이 생기면 작성 권장 |
| `dialogues/<상황명>.md` | 다른 입력 방식이나 진행 경로의 대화 | 독립적인 참고 가치가 있을 때 추가 |

README에는 학습 대상, 목표, 준비 사항과 비용, 시작 프롬프트, 진행 순서, 실행·확인 방법, 막혔을 때의 도움을 담아 주세요. 없는 파일을 미리 링크하지 마세요.

**AGENTS.md는 코딩 AI 에이전트가 읽고 따르는 코칭 지침입니다. 학습자가 직접 읽어야 하는 안내서는 아닙니다.** 학습자를 위한 설명은 README.md에 작성하고, 기여자는 AGENTS.md를 작성·검토하며 코칭 방식을 개선합니다. 학습자가 지침을 복사하거나 AI에게 읽도록 요청할 수는 있지만, 내용을 직접 해석하는 것을 실습의 선행 조건으로 삼지 마세요.

AGENTS에는 단계별 행동, 학습자에게 기다려 줄 시점, 파일 저장 위치, 확인 방법, 오류 대응, 종료·재개 방법을 명시해 주세요. 요청을 더 명확하게 표현하는 프롬프트 조언도 포함하되, 재입력을 강요하거나 매번 평가하지 않도록 해 주세요. 해당 지침만 전달받아도 과정을 진행할 수 있어야 합니다.

제출물은 Markdown 안내와 콘텐츠를 중심으로 구성합니다. 코드 조각은 문서에 포함할 수 있지만, 실습에서 생성한 프로그램 코드 파일은 제출하지 않습니다. 필요한 실행 결과 이미지는 개인정보를 확인한 뒤 포함할 수 있습니다.

## 채팅방을 역할별로 나누어 사용하세요

이 프로젝트에서는 메인 채팅방에서 전체 구성을 조율하고, 각 주제의 예제 채팅방에서 실습했습니다. 제작 중의 기술적인 논의가 학습자 역할의 대화에 섞이지 않도록 별도 채팅방을 사용하기도 했습니다. 기여할 때도 이 방식을 활용할 수 있습니다.

| 채팅방 | 다룰 내용 | 다음 작업에 전달할 것 |
| --- | --- | --- |
| 메인·기획 | 전체 구조, 주제의 범위, 공통 원칙과 문서 구성 | 확정한 목표와 문서 변경 사항 |
| 주제별 실습 | 해당 주제의 학습자 역할로 실제 진행 | 막힌 지점, 질문, 결과 확인 기록 |
| 조정·문제 해결 | 개발 지식이 필요한 원인 분석과 개선 | 개입 프롬프트, 수정한 지침, 재검증할 항목 |
| 새 검증 | 이전 설명 없이 수정된 안내만으로 재시작 | 재현 여부, 해결 여부, 남은 문제 |

모든 작업에 네 채팅방이 필요한 것은 아닙니다. 다만 기획·디버깅 내용을 많이 공유한 대화를 그대로 초보자 실습 검증에 사용하면, 문서에 없는 설명 덕분에 성공한 것을 놓칠 수 있습니다.

**채팅을 새로 열었다고 작업 환경까지 초기화되는 것은 아닙니다.** 기존 코드, 작업 폴더의 AGENTS.md, 도구 설정 등이 결과에 영향을 줄 수 있습니다. 새 검증에서는 별도 연습 폴더나 기존 결과물이 없는 상태를 사용하고, 적용된 지침과 환경을 기록해 주세요. 기존 파일을 지워야 한다면 필요한 작업을 먼저 보관하세요.

여러 채팅이 같은 파일을 수정하는 경우에도 서로 영향을 줍니다. 한 채팅에서 변경한 파일은 다른 채팅에서 다시 읽도록 하고, 같은 파일을 동시에 편집하는 상황은 피하세요. 별도 채팅의 결론이 자동으로 공유된다고 가정하지 마세요.

## 권장 제작 흐름

### 1. 메인 채팅에서 목표와 초안 정하기

학습자가 할 일과 AI가 할 일을 나누어 README와 AGENTS를 작성합니다. 아직 실습하지 않았다면 README에 **진행 상태: 초안**이라고 표시하세요.

메인 채팅에서 사용할 요청 예시입니다.

```text
이 주제의 학습 목표와 진행 단계를 정리하고 README.md와 AGENTS.md 초안을 작성해 줘.
학습자가 직접 확인할 시점과 AI가 기다릴 시점을 명확히 해 줘.
실습 대화는 아직 없으므로 dialogues.md는 생성하지 마.
```

### 2. 주제별 채팅에서 학습자처럼 진행하기

README의 시작 안내만 따라가 보세요. 개발자만 알 수 있는 해결책을 먼저 제공하지 않고, 초보자도 할 수 있는 질문과 요청으로 진행합니다. 예를 들어 “화면이 달라”, “어느 부분을 고쳐야 하는지 모르겠어”처럼 상황을 전달해 보세요.

내용 수집, 파일 생성, 실행, 수정, 종료까지 실제로 확인하고, AI가 말한 확인과 자신이 직접 확인한 것을 구분하여 기록합니다. 실행하지 않은 결과를 성공으로 표시하지 마세요.

### 3. 개발 지식이 필요한 순간에는 별도 조정 채팅 활용하기

학습자 수준의 요청만으로 진행되지 않는다면 해당 지점을 기록하고, 필요한 경우 별도 채팅에서 원인을 분석합니다. 실습을 계속하기 위해 기술적인 프롬프트를 넣었다면 그 사실을 남겨 주세요.

```text
학습자가 이 단계에서 막혔다. 아래는 시작 지침, 실제 요청, 기대한 결과와 실제 결과다.
초보자가 놓친 안내인지, AGENTS.md의 누락인지, 환경 문제인지 검토해 줘.
이번 실행을 해결한 방법과 다음 학습자에게 필요한 문서 개선을 구분해 줘.
```

한 번 성공시키는 코드 수정만으로 마무리하지 말고, 같은 상황에서 AI가 적절히 안내하려면 무엇이 필요한지 살펴보세요.

| 발견한 문제 | 주로 반영할 곳 |
| --- | --- |
| 학습자가 시작 전에 알아야 할 준비·실행 방법 누락 | `README.md` |
| AI가 단계를 건너뛰거나 학습자의 작업을 대신 완료함 | `AGENTS.md` |
| 특정 환경에서 발생한 오류와 임시 해결책 | `maintainer-notes.md` |
| 다른 입력 방식이나 의미 있는 진행 분기 | 별도 대화 예시 |

### 4. 지침을 수정하고 새 채팅에서 다시 검증하기

수정한 문서를 저장한 뒤, 새 검증 채팅에 현재 지침과 학습용 자료만 전달해 보세요. 이전 디버깅 대화를 붙여넣지 않아도 진행되는지 확인하는 것이 목적입니다.

가능하면 새 연습 폴더에서 시작하고, 영향을 받는 단계와 이후 흐름을 확인합니다. 전체 과정을 다시 검증하지 않았다면 확인한 범위를 명시하세요. AI 도구, 확인 날짜, 문서 버전, 주요 환경 차이와 남은 제한도 짧게 기록합니다.

### 5. 대표 대화를 정리하고 PR 제출하기

실습이 안정되면 실제 기록을 바탕으로 dialogues.md를 정리합니다. 문서 개선과 재검증을 마치지 못한 초안도 PR로 논의할 수 있습니다. 완성한 범위와 남은 과제를 명확히 적어 주세요.

## maintainer-notes.md: 다음 기여자를 위한 제작·개선 노트

작업 중 적용한 아이디어, 선택 이유, 각종 메모, 시행착오와 이슈를 모읍니다. 관리자뿐 아니라 이 콘텐츠를 이어서 개선할 모든 기여자를 위한 문서입니다. 학습 안내인 README나 대표 대화인 dialogues에 넣기 어려운 제작 배경을 이곳에 남겨 주세요.

전체 채팅이나 도구 실행 로그를 전부 복사할 필요는 없습니다. 다음 기여자가 판단을 이해하고 개선을 이어갈 만큼 기록하세요. 학습자나 실습 AI가 필수로 읽게 만들지는 마세요. 학습 진행에 꼭 필요한 내용은 확인한 뒤 README나 AGENTS에 반영하고, 노트에는 변경 이유와 확인 결과를 남깁니다.

- 적용한 아이디어와 선택 이유
- 시도했지만 채택하지 않은 방법과 그 이유
- 작업 중 발견한 이슈, 임시 대응과 해결 방법
- 개발자의 개입 내용과 지침 반영 여부
- 실습·재검증 결과와 남은 과제
- 다음 기여자가 알아두면 좋은 사항

다음 구조를 참고할 수 있습니다.

```markdown
# 제작·개선 노트

## 아이디어와 결정

- 제안한 아이디어와 기대 효과:
- 적용 여부와 선택 이유:
- 시도했지만 채택하지 않은 방법:
- 관련 문서 변경:

## 확인 환경

- 확인 날짜:
- 사용한 AI 도구와 확인 가능한 모델 정보:
- 기준 문서: 커밋 또는 문서 변경 설명
- 시작 상태: 새 채팅 여부, 기존 결과물 여부, 적용 지침

## 문제: 학습자 확인 전에 다음 단계가 생성됨

- 발생 단계와 학습자의 요청:
- 기대한 결과와 실제 결과:
- 개발자가 개입한 프롬프트와 필요한 기술 지식:
- 이번 실행에서 취한 조치:
- README 또는 AGENTS에 반영한 내용:
- 새 채팅에서 재검증한 범위와 결과:
- 남은 문제:

## 메모와 후속 과제

- 다음에 확인하거나 시도할 내용:
- 다음 기여자가 알아둘 사항:
```

필요한 항목만 사용하고, 아이디어와 확인된 결론은 구분해 주세요. 모델 정보처럼 확인할 수 없는 항목은 추측하지 말고 ‘확인하지 못함’으로 적어도 됩니다. 수정이 여러 번 이루어졌다면 주제나 문제별로 기록을 이어 붙이세요.

## 대화 예시를 정리하는 기준

**학습자가 보는 대표 대화와 개발자가 조정한 기록을 구분하되, 성공에 필요했던 개입을 숨기지 마세요.**

- 실제 기록을 편집한 것인지, 설명을 위해 만든 가상 예시인지 첫머리에 표시합니다. 대화 밖의 편집자 안내는 이탤릭 등으로 구별합니다.
- 실제 기록에 없던 성공이나 검증 결과를 추가하지 않습니다. 여러 실행을 합쳤다면 그 사실을 표시합니다.
- 개발자의 개입이 있어야 진행됐다면 해당 지점에 짧은 편집자 주석을 남기거나 maintainer-notes.md의 관련 항목을 연결합니다. 지침에 반영했더라도 새 실행에서 해결됐는지는 별도로 표시합니다.
- 도구 실행 로그와 `<details>...</details>` 같은 불필요한 내역은 제거할 수 있습니다. 학습 흐름과 시행착오를 이해하는 데 필요한 대화는 보존합니다.
- 개인정보, 비밀번호, API 키, 비공개 문서 내용은 제거하거나 예시 값으로 바꿉니다. 다른 사람의 대화를 공개하려면 공개 가능한 자료인지 확인합니다.
- 개인 컴퓨터의 절대 경로와 고정된 줄 번호는 제거합니다. 실제 경로와 줄 위치는 사용자마다 다르다는 안내를 문서 위에 적습니다. 생성되는 로컬 파일은 동작하지 않는 링크 대신 파일명이나 상대 경로로 표시합니다.
- 화자를 일관되게 표시하고, 표와 코드 블록이 올바르게 표시되는지 Markdown 미리보기로 확인합니다. 코드에는 언어를 지정하고, 인용문 안의 표·코드에는 인용 표시와 들여쓰기를 일관되게 적용합니다.

실습 기록이 아직 없다면 dialogues.md 없이 제출하세요. 실제로 따라 해 본 것처럼 보이는 대화를 만들어 빈칸을 채울 필요는 없습니다.

## 버전과 여러 대화 관리

AGENTS.md는 **현재 권장본 하나**를 유지하는 것을 기본으로 합니다. 오탈자 수정이나 단계 개선 같은 이력은 Git 커밋으로 관리합니다. 과거 대화가 어떤 지침을 사용했는지 필요할 때 커밋이나 태그를 함께 기록하세요. 커밋 전 기록이라면 변경 내용을 설명하고, 제출 시 대응하는 버전을 명확히 합니다.

서로 다른 입력 방식이나 학습 경로를 보여 주려면 `dialogues-v1.md`, `dialogues-v2.md`보다 의미가 드러나는 이름을 권합니다.

```text
solutions/<주제명>/
├── README.md
├── AGENTS.md
├── dialogues.md
├── maintainer-notes.md
└── dialogues/
    ├── from-pdf.md
    └── manual-input.md
```

이 구조는 선택 사항입니다. 대표 대화 하나면 충분할 수 있습니다. 여러 개를 넣으면 README에서 차이와 추천 대화를 안내하세요.

서로 다른 코칭 전략을 비교해야 해서 별도 지침이 필요하다면 실험용 문서를 구분하여 두고, 적용 대상·기준 버전·대응 대화를 명시하세요. 코딩 AI 에이전트가 기본으로 읽고 따를 파일은 계속 AGENTS.md로 유지합니다. 지침만 조금씩 다른 파일을 설명 없이 늘리거나 모두 읽도록 요구하지 마세요.

## 준비 상태를 솔직하게 표시하세요

README 상단에 다음처럼 적을 수 있습니다.

```text
진행 상태: 실습 확인
확인 범위: 기본 입력부터 결과 확인까지. PDF 입력은 아직 확인하지 않음.
대화 예시: 준비 중
```

‘초안’은 문서 작성 단계, ‘실습 확인’은 명시한 환경과 범위에서 실제로 따라 해 본 상태입니다. 대화 예시 제공 여부는 따로 표시합니다. 대화 파일이 존재한다는 사실만으로 검증 완료를 의미하지는 않습니다.

## Pull Request 보내기

저장소를 포크하거나 작업 브랜치에서 변경을 준비하고 PR을 보내 주세요. 관리자가 검토한 뒤 반영합니다. 주제와 범위에 논의가 필요하다면 먼저 Issue로 제안해도 됩니다.

PR에는 다음 내용을 간단히 담아 주세요.

- 학습 대상과 완성할 결과물
- 학습자가 직접 참여하는 방식
- 추가·변경한 문서와 준비 상태
- 실제 확인한 환경·범위·결과
- 개발자의 개입 여부, 지침 반영과 재검증 여부
- 남은 문제나 검토받고 싶은 부분

제출 전에는 문서의 상대 링크, 표와 코드 블록 표시, 시작 프롬프트와 AGENTS의 일관성을 확인해 주세요. 불필요한 원본 자료·개인정보·생성 코드가 포함되지 않았는지도 살펴보세요. 범위가 작은 설명 수정은 그에 맞는 확인만 해도 됩니다.

오탈자 수정, 설치 안내 개선, 학습 중 막힌 지점의 보고도 환영합니다. 완벽한 과정을 한 번에 제출하기보다, 확인된 범위와 개선 근거를 함께 쌓아 가고자 합니다.
